# Витрина `revenue` в ClickHouse

Решение второй части тестового задания Data Engineer (текст задания: [docs/TASK.md](docs/TASK.md)).
Витрина `revenue` переезжает из суточного pandas-скрипта в ClickHouse и обновляется 6 раз в сутки:
восемь таблиц MariaDB грузятся в сырой слой без полного чтения больших таблиц, витрина
`mart.revenue` пересобирается целиком и публикуется только после проверок, на стенде результат
дополнительно сверяется с независимым эталоном. Прогоны запускает Airflow.

**Коротко о решениях**

- **Хранилище:** ClickHouse 25.8, слои `raw` → `stg` → `mart`, пользователи `loader` и `analyst` (только `SELECT` на опубликованную `mart.revenue`).
- **Загрузка:** `users`, `plans`, `payment_systems` целиком с атомарной подменой; большие таблицы инкрементом
  по `id`; `pending`-платежи перечитываются; удаления и отзыв платежей ловит сверка по бакетам `id`.
- **Витрина:** полная пересборка в `revenue_new`, публикация `EXCHANGE TABLES` только после блокирующих проверок.
- **Оркестрация:** Airflow, DAG `revenue` раз в 4 часа и ночной `revenue_audit`; логика в пакете `pipeline`, DAG только порядок и повторы.
- **Проверка:** витрина совпала с независимым эталоном на pandas после каждого из семи прогонов.

## Запуск

Нужны Docker, Docker Compose v2 и Python 3 на хосте (только стандартная библиотека). Пароли и пользователи
лежат в `.env`, его в репозитории нет: `solution/init_env.py` создаёт его из [.env.example](.env.example)
со случайными паролями (один раз, существующий `.env` не трогает).

```bash
python3 solution/init_env.py && make reset   # .env, затем чистый стенд: MariaDB с данными, ClickHouse, Airflow
python3 solution/run_day.py                  # сутки: семь прогонов DAG, между ними make next, три выгрузки в results/
```

`--verify` после каждого прогона дополнительно сверяет витрину с эталоном. Это тестовый режим стенда:
он читает MariaDB целиком, в проде его нет.

Один прогон без имитации суток: `docker compose exec airflow airflow dags test revenue`.
UI Airflow: <http://localhost:8080> (на стенде без логина, порт открыт только на localhost).

Ручные команды того же кода без Airflow: `docker compose run --rm pipeline <run|ddl|load|mart|check|audit|verify|export <имя>>`.
`export <имя>` пишет `results/revenue_<имя>.csv`.

Контейнер пайплайна работает от пользователя хоста `1000:1000`; при другом uid задайте
`PIPELINE_USER=uid:gid` в `.env`, иначе выгрузка в `results/` упадёт по правам.

## Как устроено

```
MariaDB (app) ──► raw.*  (ReplacingMergeTree, копии таблиц + _version, _deleted)
                    │
                    ▼
                  stg.*  (представления: одна актуальная версия строки, без удалённых)
                    │
                    ▼
            mart.revenue  (сборка в revenue_new -> блокирующие проверки -> EXCHANGE TABLES)
                    │
                    ▼
       инварианты витрины -> meta.check_results;  verify (стенд): сверка с источником, эталон на pandas

Airflow (solution/dags/): DAG revenue раз в 4 часа, DAG revenue_audit раз в сутки
```

| Где | Что |
|---|---|
| `docker-compose.override.yml` | ClickHouse 25.8 на именованном volume; Airflow 3.3 (`standalone`) и Postgres для его метаданных; сервис `pipeline` для ручных команд (профиль `tools`) |
| `solution/ddl/*.sql` | DDL по слоям и пользователи. Применяется по порядку имён, все запросы идемпотентны |
| `solution/sql/revenue_build.sql` | сборка витрины в `revenue_new` |
| `solution/pipeline/` | Python: `config` (окружение или Airflow Connections), `ch` (клиенты), `ddl`, `load`, `mart`, `checks`, `cli` |
| `solution/dags/` | DAG `revenue` и `revenue_audit`; задачи только вызывают функции из `pipeline` |
| `solution/airflow.Dockerfile` | образ Airflow плюс клиент ClickHouse |
| `solution/run_day.py` | сутки на стенде: семь прогонов DAG между `make next`, три выгрузки |
| `results/` | `revenue_state0.csv`, `revenue_state3.csv`, `revenue_final.csv` |
| `solution/tests/` | pytest: сценарии вне пакетов и идемпотентность, структура DAG, замер на 100-кратном объёме |

## Хранилище

**Данные переживают перезапуск:** `/var/lib/clickhouse` на именованном volume `clickhouse_data`;
`make reset` сносит его вместе со стендом, `docker compose restart` нет.

**Пользователи и права.** Три пользователя, пароли только из `.env`:

| Пользователь | Создаёт | Права |
|---|---|---|
| `admin` | образ ClickHouse из переменных окружения | всё; используется только для DDL и создания пользователей |
| `loader` | `solution/ddl/90_users.sql` | `SELECT, INSERT, ALTER, TRUNCATE, CREATE TABLE, DROP TABLE` на `meta`, `raw`, `mart`; `SELECT` на `stg`. Под ним работают загрузка, сборка витрины, проверки и выгрузка. Создать базу или пользователя не может |
| `analyst` | то же | только `SELECT` на опубликованную `mart.revenue`: право на таблицу, а не на `mart.*`, поэтому `mart.revenue_new` до проверок аналитику не видна, а после `EXCHANGE TABLES` право по имени действует на новую версию. Профиль с `readonly = 2`, лимитами памяти (4 ГБ) и времени запроса (300 с); лимиты помечены `CONST`, переопределить их в запросе нельзя. Доступа к `stg` и `raw` нет: представления `stg` выполняются с правами читающего и потребовали бы `SELECT` на `raw` |

Пользователи создаются через `CREATE USER IF NOT EXISTS` плюс `ALTER USER ... IDENTIFIED BY`, профиль
через `CREATE SETTINGS PROFILE IF NOT EXISTS` плюс `ALTER SETTINGS PROFILE` (так он сохраняет id и не
отвязывается от пользователя), права `analyst` одним `GRANT ... WITH REPLACE OPTION`, который атомарно
заменяет всё выданное раньше. Поэтому повторное применение DDL не падает и подхватывает смену пароля,
прав или лимитов в `.env` и DDL. Значения из `.env` подставляются в DDL только
после проверки: символы, способные разорвать запрос (`;`, `--`, кавычка, обратный слеш, перевод
строки), запрещены с понятной ошибкой.

**Слои и движки.**

| Слой | Движок | Зачем |
|---|---|---|
| `raw` | `ReplacingMergeTree(_version, _deleted) ORDER BY id`; большие таблицы партиционированы по месяцу неизменяемой даты (`created_at`, `activated_at`, `usage_date`) | копия источника как есть. Маркер удаления = та же строка с `_deleted = 1` и большей версией. Повторная запись той же строки не создаёт дубля, поэтому загрузка идемпотентна |
| `stg` | представления `SELECT ... FROM raw.<t> FINAL WHERE _deleted = 0` | одна актуальная версия строки без служебных колонок. На стенде представления; в проде для таблиц от десятков миллионов строк их материализует dbt |
| `mart` | `MergeTree ORDER BY order_id` | витрина `revenue`, 17 колонок по ТЗ в том же порядке |
| `meta` | `MergeTree` | `load_runs`: каждый шаг загрузки каждого прогона (стратегия, диапазон `id`, число строк, ошибка, если шаг упал); `check_results`: каждая проверка каждого прогона, включая блокирующие до публикации |

Почему партиция по месяцу: маркер удаления копирует последнюю версию строки, значит ключ партиции
у него тот же, и схлопывание версий внутри одной партиции гарантировано. Партиция по изменяемой
колонке развела бы версии по разным партициям.

## Загрузка источника

У всех таблиц `id` AUTO_INCREMENT и нет `updated_at`. Отсюда две основные стратегии и два механизма
поверх них для строк, которые меняются после вставки.

| Таблица | Стратегия | Почему |
|---|---|---|
| `users`, `plans`, `payment_systems` | полная перезагрузка: таблица целиком в `raw.<t>_new`, затем `EXCHANGE TABLES` | таблицы маленькие (ТЗ разрешает читать их целиком), а в `users` старые строки меняются без срока давности: пользователя помечают тестовым задним числом. Полная копия отражает любое изменение и удаление, подмена атомарна |
| `orders`, `activations`, `usage_daily`, `refunds`, `payments` | инкремент по `id`: `WHERE id > max(id) в raw - 1000 ORDER BY id LIMIT 50000` порциями | новые строки, в том числе опоздавший расход за прошлые дни и досланные платежи, всегда имеют новый `id`; запрос идёт по первичному ключу и читает только их. Запас в 1000 `id` назад покрывает транзакции, зафиксированные не по порядку `id`, повторно прочитанные строки схлопываются |
| `payments` | **перечитка `pending`** | статус меняется в течение 72 часов, а иногда позже. Все платежи, которые в `raw` ещё `pending`, перечитываются по `id` каждый прогон, какого бы возраста они ни были: это список из `stg` и выборка по первичному ключу |
| `orders`, `payments` | **сверка по бакетам `id`** после инкремента | источник удаляет мошеннические заказы вместе с платежом. По бакетам в 10 000 `id` сравниваются число строк и сумму `id`: в MariaDB это обход вторичного индекса без чтения строк (`EXPLAIN`: `type: index, Using index`). Для `payments` дополнительно хеш `CRC32(CONCAT(id, status))`, но только по `id` платежей моложе 30 дней: диапазон по первичному ключу (`type: range`). Расходящиеся бакеты разбираются по `id`: исчезнувшие строки получают маркер удаления, изменённые перечитываются. Полный хеш по всей таблице делает команда `audit` раз в сутки. Это правило бюджета из первой части: таблицы меньше 1 ГБ сверяются целиком каждый прогон и хешируются каждую ночь, а большие изменяемые таблицы прода сверяют по индексу ночью и хешируют раз в неделю по ротации, не больше 15 ГБ чтения с реплики за ночь |

Детали, которые важны для корректности:

- **«Сейчас» берётся по часам источника,** а не по часам сервера: стенд проигрывает сутки за минуты,
  а в проде реплика может отставать. Это последняя строка по первичному ключу в `orders` и `activations`
  и максимум `created_at` по индексу в `payments`: три обращения к индексу, без сканов.
- **Часовой пояс явный.** Даты из MariaDB приходят без пояса, и все они в UTC. Перед вставкой в ClickHouse
  и в параметрах запросов им проставляется UTC: clickhouse-connect переводит datetime через `timestamp()`
  и `astimezone()`, и время без пояса посчитал бы местным временем процесса. Поэтому результат не зависит
  от `TZ` контейнера или хоста; без этого при `TZ=+07` все даты сдвигались на 7 часов.
- **Водяной знак** это `max(id)` в самой raw-таблице, а не отдельная запись состояния: упавший на середине
  прогон безопасен, следующий просто продолжит с того, что реально записано.
- **Версия одна на весь прогон:** микросекунды текущего времени, но не меньше уже записанной версии + 1,
  поэтому строка из следующего прогона всегда побеждает, даже если часы сервера ушли назад. Если строка
  прочитана за прогон дважды (инкрементом и перечиткой `pending` или сверкой), версии равны и
  ReplacingMergeTree оставляет последнюю записанную; обе прочитаны из источника с разницей в секунды.
- **Сверка ловит не только удаления.** Хеш статуса в `payments` поймает `success -> declined` без
  участия `pending`, в том числе у старых платежей при полном `audit`. Удаления в `activations`,
  `usage_daily` и `refunds` ТЗ не обещает, поэтому сверка для них не включена; включается одной строкой
  в `RECONCILE_TABLES`.
- **Что читается из MariaDB за прогон:** новые строки по первичному ключу; `pending`-платежи по `id`;
  для `orders` и `payments` обход вторичного индекса (число строк и сумма `id`) и строки `payments`
  за последние 30 дней по диапазону первичного ключа. Ни одна большая таблица не читается целиком.

## Витрина `mart.revenue`

**Полная пересборка, а не инкремент.** Поля истории пользователя (`first_paid_at`, `first_cohort`,
`month_since_first`, `purchase_number`) меняются у старых строк при любом новом или отозванном платеже
этого пользователя, а пометка пользователя тестовым убирает все его строки. Корректный инкремент
означает пересчёт всех строк затронутых пользователей, то есть ту же логику плюс учёт затронутых.
При текущем объёме (56 тысяч строк) ClickHouse пересчитывает витрину за секунды, на 100-кратном
около 10 секунд (замер ниже), поэтому инкремент не окупается.

**Публикация после проверок.** Пересборка идёт в `mart.revenue_new`, затем блокирующие проверки, и только
после них `EXCHANGE TABLES`. Если проверка не прошла, прогон падает, а аналитики продолжают видеть прежнюю
витрину: для финансовой витрины вчерашние верные цифры лучше свежих с ошибкой. Блокируют только проверки,
ошибка в которых даёт неверные цифры:

| Проверка `revenue_new` | Порог |
|---|---|
| Структура: не пуста, `order_id` уникален, у каждого заказа есть план | любое нарушение |
| Бизнес-правила: нет тестовых и сотрудников, у payment-строк платёж `success`, у points-строк нулевая выручка, `gross_profit = revenue - cogs`, `purchase_number` без пропусков, `first_paid_at` равен первому платежу, каждый подходящий заказ ровно один раз | любое нарушение |
| Число строк против прошлой версии | падение > 2% или рост > 10%, но не меньше 100 строк (иначе маленький набор данных срабатывал бы на обычном пакете) |
| Сумма success-платежей за 7 дней в `stg` против MariaDB (диапазон по индексу `created_at`) | > 0,5% блокирует, 0,1–0,5% — предупреждение в логе |

Свежесть и объём загрузки публикацию не блокируют: устаревшие данные не неверные. Сравнение с прошлой версией
и с источником выключается переменной `MART_BASELINE_CHECKS=0` только в синтетическом замере ×100.

**Логика** ([solution/sql/revenue_build.sql](solution/sql/revenue_build.sql)) повторяет ТЗ буквально:
отбор заказов по текущему состоянию `users` и статусу `success`, `paid_at` из платежа или заказа,
категория пакета через `multiIf`, возвраты и себестоимость агрегатами по `payment_uid` и по цепочке
`usage_daily -> activations -> order_id`, поля истории оконными функциями по `user_id`.

Решения, которых в ТЗ нет явно:

- `payment_uid` в витрине всегда строка, для заказов за баллы пустая. `first_paid_at`, `first_cohort`
  и `purchase_number` для «пусто» используют NULL; в CSV NULL выгружается пустым полем.
- Заказ с непустым `payment_uid`, платёж по которому ещё не пришёл, в витрину не попадает и появится,
  когда платёж дойдёт.
- План присоединяется через `LEFT JOIN`: заказ с неизвестным планом не пропадает из витрины молча,
  а останавливает публикацию блокирующей проверкой.
- Суммы хранятся как `Decimal(10, 2)` и в CSV печатаются с двумя знаками.

Результат каждой блокирующей проверки, прошла она или нет, пишется в `meta.check_results` с префиксом
«до публикации: » и измеренным значением ещё до решения о публикации.

**Проверки после публикации** (`check`, каждый прогон, только внутри ClickHouse): инварианты самой витрины
(уникальность `order_id`, нулевая выручка у `points`, `gross_profit`, нумерация `purchase_number`,
`first_paid_at`) повторяются на опубликованной `mart.revenue`. Сверки со `stg` (нет тестовых, платёж
`success`, каждый подходящий заказ ровно один раз) идут только до публикации, в одном шаге со сборкой
под pool `raw_access`: после публикации ночной `audit` может поменять `stg`, и такая проверка упала бы
на верной витрине. Результаты пишутся в `meta.check_results` для истории и дашборда, провал завершает
прогон ненулевым кодом.

**Эталон** (`verify`, только стенд): витрина считается второй раз другим способом (pandas) и из другого
места (прямо из MariaDB, минуя `raw` и `stg`) и сравнивается с `mart.revenue` поколоночно. Дополнительно
число строк и `max(id)` каждой таблицы `stg` сверяются с источником. В проде эталон считался бы по выборке
пользователей.

## Проверка корректности

Четыре уровня, описанные выше: блокирующие проверки до публикации и инварианты после неё выполняются
в каждом прогоне, сверка `stg` с источником и независимый эталон только командой `verify` на стенде.

**Тесты** ([solution/tests/](solution/tests/), pytest). Шесть пакетов стенда содержат только переходы из
`pending`, пометку тестовым и удаления. Остальные свойства источника проверяются своими SQL-файлами
([solution/tests/sql/](solution/tests/sql/)): тесты применяют их к MariaDB вне пайплайна. Правило «MariaDB
только читайте» относится к пайплайну, а не к тестам стенда. Тесты меняют источник, поэтому идут на
свежем стенде, а после них стенд возвращается командой `make reset`; повторный запуск без неё
останавливается с подсказкой.

```bash
make reset && docker compose run --rm --entrypoint pytest pipeline             # сценарии, около 30 с
docker compose exec airflow pytest solution/tests/dags                         # структура DAG, без данных
make reset && docker compose run --rm --entrypoint pytest pipeline -m scale -s # замер x100, ломает стенд
```

Сценарии ([test_scenarios.py](solution/tests/test_scenarios.py)) вызывают тот же код, что задачи DAG, но без
Airflow: тесты проверяют логику загрузки и витрины, а не расписание. После каждого шага витрина сравнивается
с эталоном на pandas:

| Шаг | Что меняется в источнике | Результат |
|---|---|---|
| идемпотентность | ничего, второй прогон подряд | число строк и хеш всех строк витрины не изменились, сверка без расхождений |
| 1 | снят тестовый флаг; пользователь стал сотрудником; план сменил категорию; свежий платёж `success -> declined`; опоздавший на 12 дней `pending`-платёж с заказом | витрина совпала с эталоном; отзыв свежего платежа пойман хешем сверки в штатном прогоне |
| 2 | опоздавший платёж подтвердился | заказ появился в витрине, витрина совпала с эталоном |
| 3 | отозван первый платёж пользователя, старше 30 дней | штатный прогон его не видит (вне окна хеша, ожидаемо); `audit` находит, следующий прогон убирает строку и пересчитывает поля истории пользователя, витрина совпала с эталоном |

Структура DAG ([tests/dags/](solution/tests/dags/test_dags.py)): оба DAG загружаются без ошибок, расписание,
`max_active_runs`, зависимости задач, повторы и pool такие, как описано в разделе «Оркестрация».

Замер ([test_scale100.py](solution/tests/test_scale100.py), маркер `scale`, в обычный запуск не входит):
данные размножаются прямо в ClickHouse в 100 раз со сдвигом ключей. Загрузку на таком стенде запускать
нельзя: сверка пометит лишние строки удалёнными. Ноутбук, один контейнер ClickHouse:

| Объём: 6,4 млн заказов, 32,8 млн строк расхода, 4 млн пользователей | Время |
|---|---|
| `SELECT count() FROM stg.usage_daily` (представление с `FINAL`) | 0,33 с |
| `stg.orders JOIN stg.users` (оба через `FINAL`) | 0,23 с |
| пересборка `mart.revenue` целиком, 5,6 млн строк, с проверками и подменой | 10,3 с |

При шести прогонах в сутки это укладывается с большим запасом. `FINAL` в представлениях `stg` и полная
пересборка витрины перестанут окупаться на объёмах ещё на порядок-два больше: тогда `stg` для больших
таблиц материализуется, а витрина пересчитывается по затронутым пользователям.

**Что показали данные стенда** (состояние после шестого пакета):

- 10 платежей пришли с опозданием до 10 дней относительно соседних `id`: `created_at` это время платёжной
  системы, инкремент по `id` их ловит, инкремент по дате потерял бы.
- 428 активаций относятся к заказам, платёж которых не `success`: сервис активирует пакет до подтверждения
  оплаты. Их расход в витрину не попадает, пока платёж не подтвердится.
- 14 возвратов относятся к платежам в статусе `declined`. Заказы у всех 14 есть, но в витрину не попадают
  из-за статуса платежа, поэтому и возвраты в ней не видны. По заказам с `declined`-платежами накоплено 2 762 строки
  расхода на 1 109,48 €: эта себестоимость не попадает ни в одну строку витрины. По ТЗ это верно, но аналитикам
  стоит знать о ней отдельной метрикой.
- После 4 мошеннических удалений активации (4) и их расход остаются в источнике без заказа.
- 19 549 строк расхода записаны не в порядке дат: опоздание расхода это норма, а не исключение.
- 12 платежей остаются `pending` в конце суток; `payment_uid` ни разу не повторяется у разных заказов.
- Между `state0` и `final`: 137 новых строк, 16 исчезли (удаления и пользователи, помеченные тестовыми),
  654 изменились: у 640 выросла себестоимость, у 10 появился возврат, у 10 сменился `purchase_number`,
  у 8 `first_paid_at`. Это и есть «поля истории меняются у старых строк» из ТЗ.

## Оркестрация

**DAG `revenue`** ([solution/dags/revenue.py](solution/dags/revenue.py)), каждые 4 часа:

```
ddl ─► load_users, load_plans, load_payment_systems, load_activations, load_usage_daily, load_refunds ─┐
    ├► load_payments ─► reread_pending ─► reconcile_payments ───────────────────────────────────────────┼─► build_mart ─► check_mart
    └► load_orders ─► reconcile_orders ─────────────────────────────────────────────────────────────────┘
```

- Загрузки таблиц независимы и идут параллельно (`LocalExecutor`).
- `max_active_runs=1`: два прогона одновременно не пишут в `raw` и не подменяют витрину.
- Pool `raw_access` ([solution/airflow_pools.json](solution/airflow_pools.json), 8 слотов): все задачи,
  которые пишут в `raw` или собирают из него витрину, берут по слоту, аудит берёт все восемь. Версия строки
  назначается в начале задачи, поэтому два писателя одной таблицы одновременно могли бы записать более старое
  чтение источника с большей версией. Pool исключает это без жёсткой привязки к расписанию. `check_mart`
  в pool не входит: он читает только опубликованную `mart.revenue`, которую меняет лишь `build_mart`.
- Загрузки повторяются 2 раза через 5 минут: они идемпотентны, повтор безопасен. `build_mart` и `check_mart`
  не повторяются: провал блокирующей проверки повтором не лечится.
- `catchup=False`: пропущенный интервал догонять не нужно, следующий прогон заберёт всё новое по водяному знаку.
- Все задачи одного запуска пишут в `meta.load_runs` и `meta.check_results` с одним `run_id`, производным
  от `run_id` Airflow.

**DAG `revenue_audit`** ([solution/dags/revenue_audit.py](solution/dags/revenue_audit.py)), в 02:00, между
прогонами `revenue`: полная сверка `orders` и `payments` с хешем по всей таблице. Исправления пишутся в `raw`,
витрину пересобирает ближайший прогон `revenue`. Если прогон `revenue` затянется до 02:00, аудит дождётся
свободного pool: проверено одновременным запуском обоих DAG планировщиком.

**Почему Airflow.** Это решение из первой части (ADR 0003 «Оркестратор — Apache Airflow»):
стандарт, который знает большинство инженеров, поэтому систему одного DE сможет принять другой человек.
Слой тонкий: DAG задаёт порядок, повторы и расписание, а логика живёт в пакете `pipeline` и запускается
и без Airflow (CLI выше). Cron с `flock` закрыл бы расписание и защиту от параллельных запусков, но не дал бы
зависимостей между шагами, повторов отдельного шага, истории запусков и UI, где видно, какой шаг упал.

**На стенде и в проде.** На стенде Airflow одним контейнером `airflow standalone` (планировщик, обработчик DAG,
API и UI), DAG создаются на паузе: сутки имитирует `make next`, а `run_day.py` запускает тот же DAG синхронно
(`airflow dags test`). В проде те же DAG сняты с паузы, компоненты Airflow отдельными сервисами,
подключения приходят из зашифрованных секретов при деплое.

**Подключения.** Адреса и пароли MariaDB и ClickHouse задачи берут из Airflow Connections (`mariadb_app`,
`clickhouse_admin`, `clickhouse_loader`, `clickhouse_analyst`). На стенде их задаёт `docker-compose.override.yml`
из `.env`; в проде пароли лежат в репозитории зашифрованными (SOPS + age) и попадают в Connections при деплое,
код DAG не меняется.

## Как это поддерживать

**Загрузка упала.** Airflow сам повторит задачу дважды. Если повторы не помогли, задача красная в UI, лог
шага там же, а в `meta.load_runs` шаг записан со статусом `failed` и текстом ошибки. После исправления причины
задачу перезапускают из UI (Clear), зависимые шаги пойдут за ней. Водяной знак это `max(id)` в raw, порции
уже записанных строк при повторе схлопнутся, витрина до конца загрузки не трогается и остаётся на последней
удачной версии.

**Витрина не опубликована.** Проваленная блокирующая проверка названа в логе и в исключении и записана
в `meta.check_results` (`passed = 0`, префикс «до публикации: », измеренное и ожидаемое значение);
аналитики видят прежнюю версию. Исправить причину в данных или в сборке и перезапустить `build_mart` из UI.

**Данные разошлись с источником.** Для `orders` и `payments` сверка находит и исправляет расхождение сама
при следующем прогоне; число расхождений видно в `meta.load_runs` (шаги `reconcile` и `audit`). Для остальных
таблиц: `TRUNCATE raw.<t>` и прогон, таблица перечитается целиком (на стенде секунды; в проде для этого есть
ночное окно, либо сверку включают для этой таблицы в `RECONCILE_TABLES`). Витрина после этого пересобирается
штатно: она всегда производная от `raw`.

**Сигналы на стенде.** Упавшая задача красная в UI Airflow, после повторов DAG завершается ошибкой. Каждый шаг
загрузки пишется в `meta.load_runs` (статус, диапазон `id`, число строк, текст ошибки), каждая проверка витрины —
в `meta.check_results`. Блокирующие проверки не дают опубликовать неверную витрину. Сами никому эти сигналы
не приходят: канала дежурного на стенде нет.

**Алерты в проде** строятся на тех же таблицах, код пайплайна не меняется:

- провал задачи после повторов — `on_failure_callback` в `DEFAULT_ARGS` DAG, сообщение в канал дежурного;
- витрина не опубликована или провалились инварианты — тот же callback, в тексте названа проверка;
- свежесть, heartbeat и рост расхождений сверки — внешняя проверка раз в 15 минут выполняет запросы ниже под
  пользователем `loader` (у него есть `SELECT` на `meta`) и шлёт алерт по порогам. Внешняя, потому что
  упавший планировщик Airflow не сообщит, что он молчит;
- дашборд Grafana поверх `meta.*` и `system.*` ClickHouse с теми же метриками.

**Запросы для проверок.** Их можно выполнить на стенде прямо сейчас.

Свежесть: последняя успешная загрузка каждой таблицы. Алерт DE, если больше 300 минут (5 часов).

```sql
SELECT
    table_name,
    max(finished_at)                   AS last_ok,
    dateDiff('minute', last_ok, now()) AS minutes_ago
FROM meta.load_runs
WHERE status = 'ok' AND strategy IN ('full', 'incremental')
GROUP BY table_name
ORDER BY minutes_ago DESC
```

Heartbeat: последний прогон, в котором витрина опубликована и все инварианты прошли. Алерт, если больше
300 минут или строк нет. Прогоны `verify` сюда не попадают: в них нет инвариантов витрины.

```sql
SELECT
    max(checked_at)                        AS last_ok_run,
    dateDiff('minute', last_ok_run, now()) AS minutes_ago
FROM
(
    SELECT run_id, max(checked_at) AS checked_at
    FROM meta.check_results
    GROUP BY run_id
    HAVING countIf(check_name = 'order_id уникален') > 0 AND min(passed) = 1
)
```

Сверка: число расходящихся бакетов по дням. Алерт, если за сутки в 10 раз больше обычного: сверка сама чинит
`raw`, но такой рост значит, что в источнике что-то поменялось.

```sql
SELECT
    toStartOfDay(started_at)                                AS day,
    table_name,
    sum(toUInt64OrZero(extract(note, 'mismatched (\\d+)'))) AS mismatched_buckets
FROM meta.load_runs
WHERE strategy IN ('reconcile', 'audit') AND status = 'ok'
GROUP BY day, table_name
ORDER BY day DESC, table_name
```

## Отступления от архитектуры части 1

Стенд — это срез минимальной версии из части 1: один источник, одна витрина. Формат `raw`, стратегии загрузки,
правило бюджета сверки, публикация после блокирующих проверок и Airflow совпадают. Отличается следующее:

| В части 1 | На стенде | Почему | В проде |
|---|---|---|---|
| Трансформации и тесты в dbt | Один SQL-файл и проверки на Python | Одна витрина без графа зависимостей, dbt не окупается | `revenue_build.sql` почти дословно становится dbt-моделью, проверки — dbt-тестами |
| Контракт колонок со сверкой схемы по `information_schema` | Списки колонок зашиты в `load.py`, изменения схемы не отслеживаются | Схема стенда неизменна | Задача в DAG: сверка схемы, алерт на новую колонку, стоп таблицы при удалении или смене типа |
| Семь проверок качества | Блокирующие проверки до публикации есть; свежесть — готовый запрос без алерта; объёма загрузки (±30%) и кабинетов нет | Сутки имитируются `make next`, свежесть и объём на стенде ничего не значат | Свежесть и объём по `meta.load_runs`, алерт DE без блокировки публикации |
| Роли: загрузка пишет в `raw`, dbt — в `stg` и `mart` | Один пользователь `loader` пишет во все слои | Без dbt нет второго писателя | Отдельный пользователь dbt с правами только на `stg` и `mart` |
| Секреты в репозитории под SOPS + age | `.env` со случайными паролями из `init_env.py` | Локальный стенд | Зашифрованный файл в репозитории, расшифровка при деплое |
| MinIO для бэкапов и PostHog | MinIO нет | На стенде нет PostHog, бэкапы ТЗ не требует; данные переживают рестарт за счёт тома | `clickhouse-backup` в MinIO на отдельном хосте |
| Аналитики читают `stg` и `mart` | `analyst` читает только `mart.revenue` | Так требует ТЗ; представления `stg` выполняются с правами читающего и потребовали бы доступа к `raw` | Представления `stg` с `SQL SECURITY DEFINER`, аналитикам открыты `stg` и `mart` |
| К MariaDB пайплайн ходит пользователем только с `SELECT` | `root` | На стенде MariaDB — чужой сервис, создавать в ней пользователей запрещено | Отдельный пользователь с `SELECT` на нужные таблицы |
| Схема `pii`, HMAC вместо email и телефона в `stg` | Нет | В данных стенда нет ПДн: у пользователей только страна и флаги | Как в части 1 |
| Алерты в канал дежурного, внешний heartbeat | Сигналы в UI Airflow и в `meta`, готовые запросы свежести, heartbeat и сверки | На стенде нет канала дежурного, сутки имитируются `make next` | `on_failure_callback` в канал, внешняя проверка запросов из раздела «Как это поддерживать» |
| Дашборд Grafana и runbook на каждый алерт | Нет | Объём задания | Дашборд по `meta.*` и `system.*`, runbook в репозитории |

CDC на стенде не используется, хотя бинлог включён. Это не отступление: в части 1 CDC — первый шаг плана роста,
а минимальная версия от бинлога не зависит.

## Что иначе в проде и что не сделано

- **Бинлог как следующий этап.** Включён ли бинлог на реплике, неизвестно, поэтому решение от него не зависит:
  опрос по `id` с перечиткой `pending` и сверкой закрывает все свойства источника из ТЗ. Цена опроса в том, что
  удаления и правки в таблицах без `updated_at` видны только сверкой. Триггер, как в плане роста части 1: сверка
  не укладывается в бюджет 15 ГБ за ночь или правки старых строк нужны быстрее 7 дней. Тогда `raw` наполняется из бинлога: встроенный Debezium без Kafka (Altinity clickhouse-sink-connector
  пишет прямо в `raw`). Kafka появится, когда у потока изменений будет второй потребитель: для одного
  потребителя это три лишних компонента в эксплуатации. Для этого на реплике
  нужны `log_bin`, `binlog_format=ROW`, `binlog_row_image=FULL`, `log_slave_updates=ON` (реплика пишет в свой
  бинлог то, что получила от мастера), срок хранения бинлога в несколько суток и пользователь с правами
  `REPLICATION SLAVE, REPLICATION CLIENT`; включают это администраторы базы. Контракт `raw` при этом не
  меняется (те же таблицы, `_version` и `_deleted`), поэтому `stg` и витрина остаются как есть, а опрос
  остаётся начальным снимком и аудитом. Архитектура из первой части предлагает тот же порядок: опрос сразу,
  бинлог после того, как его включат на реплике.
- **`stg` для больших таблиц** материализуется (dbt incremental), когда p95 чтения через `FINAL` превысит 5 с;
  на 100-кратном объёме `count()` через `FINAL` занимает 0,33 с (замер выше).
- **Витрина инкрементально** по затронутым пользователям, когда полная пересборка займёт больше 30 минут;
  на 100-кратном объёме она занимает 10 с, с ночной полной пересборкой как контролем.
- **Бэкапы и отказоустойчивость.** `clickhouse-backup` в MinIO на отдельном хосте: полный раз в неделю, инкремент ежедневно;
  второй узел с репликацией, когда диск занят больше чем на 70%, p95 запросов аналитиков больше 30 с
  или от хранилища зависят продуктовые функции.
- **DDL отдельным шагом.** Сейчас первая задача DAG применяет DDL под `admin` при каждом прогоне, чтобы чистый
  стенд поднимался сам; в проде DDL идёт миграцией при деплое, а прогон работает только под `loader`.
- **Инфраструктура кодом.** VM и сеть через Terraform, установка Docker, ClickHouse и Airflow через Ansible,
  а не руками; на стенде это заменяет один `docker-compose.override.yml`.
- **Airflow в проде:** компоненты отдельными сервисами, метаданные в ежедневном `pg_dump`, вход через SSO.
- Не сделано в рамках задания: тесты в CI на каждый pull request (сейчас запускаются руками на стенде), дашборд по `meta.*`, разбор
  `payment_uid`, общего для нескольких заказов, если такое встретится.

## Допущения

- Бинлог на реплике может быть выключен; решение его не требует.
- Все даты в источнике и хранилище в UTC.
- В `payments` `payment_uid` уникален по схеме источника (`UNIQUE KEY uk_payment_uid`), поэтому JOIN заказа
  с платежом не размножает строки. Среди заказов уникальность схемой не гарантирована, но в данных стенда
  соблюдается; при нарушении выручка и возврат попали бы в каждый такой заказ.
- Возврат относится только к заказу за деньги: заказ за баллы с пустым `payment_uid` с возвратами не
  соединяется, даже если в `refunds` окажется строка с пустым `payment_uid`.
- `activations`, `usage_daily` и `refunds` не удаляются и не правятся; при необходимости сверка для них
  включается в `RECONCILE_TABLES`.
- Изменение статуса платежа старше 30 дней ловится полным `audit` раз в сутки, а не каждым прогоном.
- Транзакции, зафиксированные не по порядку `id`, отстают не больше чем на 1000 `id` (`LOAD_OVERLAP_IDS`).
